# 实测数据：B站 字幕到底有多不可靠

这个文档放原始证据，README 里只留结论。所有数字都来自真机 / 真实接口，不是估算。

## 一、同一个视频，字幕接口会返回不同文件

2026-11-13，用户自己的课 `BV1JynA6aEug`（401 秒，Git 那期），同一个 `(aid, cid)` 连取 8 次：

| 结果 | 次数 |
| --- | --- |
| 正确的 Git 字幕 | 5 |
| 电动车相关的字幕 | 1 |
| 时长超出视频的字幕 | 1 |
| HTML 错误页（不是字幕） | 1 |

正确的那份只出现 5/8 次。如果实现成「取第一个通过闸门的」，有一半概率把别的视频的笔记写给你——**这正是市面上字幕工具最常见的失效方式**。

更早的样本：194 秒的视频能返回 1606 秒的字幕；两个完全不同的街舞视频返回同一首歌的歌词。

## 二、60 条真实视频的可用率

随机抽 60 条视频，直接调字幕接口，按闸门判据分类：

| 结果 | 条数 |
| --- | --- |
| ok（时长覆盖 0.85~1.10） | 14 |
| overflow（字幕比视频长很多） | 17 |
| truncated（字幕只覆盖一部分） | 9 |
| emptyUrl（有轨但 url 为空） | 9 |
| noSubs（没有中文轨） | 11 |

原始数据在 `test/fixtures/probe-results.json`（60 条，含每条的时间覆盖比），`node test/realdata.test.mjs` 拿它做回归：40 条有文件的样本 **40/40 与"时长闸期望"一致**。

覆盖率分布：`<0.6: 13` / `0.6~0.85: 0` / `0.85~1.10: 10` / `>1.10: 17`。注意 0.6~0.85 是空的——接口不返回"稍微不完整"的字幕，要么基本完整，要么差一大截，这让覆盖比成为一个很干净的判据。

## 三、闸门实际判据

| 闸门 | 判据 | 失败时界面写什么 |
| --- | --- | --- |
| 存在性 | 有中文轨且 url 非空 | 这个视频没有字幕 / 字幕轨为空 |
| 时长 | 覆盖比 = 末句时间 / 视频时长，要求 0.85~1.10 | 字幕只有一部分 / 字幕比视频还长 |
| 结构 | ≥8 行、≥120 字、平均句长≥3、累计时长比≤1.15、最大空档 ≤ max(90s, 时长×10%) | 字幕结构异常 |
| 稳定 | 最多取样 5 次，按哈希投票；同一份文件拿到 3 票提前收；票数≥2 才算 stable，只有一份通过算 single | 单次取样（未复核） |
| 登录 | 未登录直接停（接口返回 0 轨） | 请先登录 B站 |

投票打平（两种文件各 2 票）或每次都不同 ⇒ 判 `ambiguous`，**不猜**，给「再试一次」。

「两次取样一致」只说明取样稳定，**不说明内容属于这个视频**（已实测到时长对得上但内容是别的视频歌词的情况），所以界面文案不写「已验证」。

## 四、真模型跑出来的数字

deepseek-flash，真实字幕 `BV1GyZYYNErW`（2132 句 / 25311 字 / 70 分钟 → 120 块）：

- 单块 prompt 约 540~633 token，输出 250~492 token，耗时 96~184 ms。
- 6 个连续块：23 条要点活下来 22 条。
- 要点的时间戳和原文**不由模型手抄**：模型只给 `sentence_ids`，时间由字幕句的 from/to 推导，引文由这些句子的原文拼接。模型若自拟引文且与所选句子二字片段命中 <50%，整条丢弃。
- 70 分钟视频全部跑完 ≈ 6~7 万 input token，几分钱到一毛钱（按 ¥1/百万 token 的便宜模型算）。面板右上角实时显示。

`node test/accept.mjs`，2026-11-14 13:16–13:19，Edge 157，deepseek-flash：**16 / 16 通过，退出码 0**。

| 样本 | 闸门 | 结果 |
| --- | --- | --- |
| 游戏区 `BV1GyZYYNErW` | stable 120 块 | 300s 出 117 条笔记 → 点时间戳跳转 → 导出 79,316 字 |
| 影视区 `BV1twZ4YzEmv` | single 65 块 | 620s 出 6 条 → 导出 8,354 字 |
| 美食区 `BV1w6ZEYrEsb` | stable 19 块 | 200s 出 1 条 → 导出 858 字 |
| 切走 95 秒 | — | 回来有补课横幅 |
| 无字幕 `BV1BtZJYBE4G` | rejected | 状态条写明「字幕和视频对不上」 |

离线单测合计 **171 条全绿**：gate 40 / vote 10 / pages 15 / section 25 / visual 9 / hardsub 61 / pipeline 11 / realdata 40 match + 0 mismatch（20 条无字幕跳过）。

## 六、画面字幕（硬字幕）兜底

有的视频字幕烧在画面里，接口返回 0 轨。v0.6.0 起可以本机 OCR 读底部字幕带：

- 1080p 硬字幕（耶鲁公开课 `BV1K5x56nEVe`，46 分钟，接口 0 轨，右下角有校徽）：100 秒出 3 条带「画面字幕（识别）」的真笔记。
- 480p 会被明确拒绝（中文字只有十几像素），提示「清晰度太低，认不出画面字幕」，不进入识别、不耗 CPU。
- 错字会进原话（读的是像素），数字、人名、公式最容易错；40 条样本里肉眼可见错字 3~5 处，不影响理解。
- OCR 引擎对比：tesseract.js（chi_sim_best）在 1080p 课件帧上基本不可用（正文被认成「在三角形 4BC 中，已知 w，D，4」），换 PP-OCRv6 tiny（ONNX Runtime Web + wasm）后同一帧几乎全对，初始化 270ms、单帧 1.3~1.5 秒，全在本机。

## 七、设置页的端点白名单（W2-1）

为什么要在保存时拦：MV3 里对**没在 `host_permissions` 声明过**的域名发 `fetch`，只会抛 `TypeError: Failed to fetch`——和断网、DNS 错、Key 错是同一句话。事后再想区分已经不可能，所以必须在用户点「保存」那一刻拦下来，并告诉他能用哪几家。

| 检查 | 行为 | 对应断言 |
| --- | --- | --- |
| 预设 6 家都在 manifest 里 | 选了预设就一定能保存 | endpoint 6 条 |
| 协议不符（只有 https 权限时填 http） | 拦 | endpoint 1 条 |
| 后缀伪装 `api.deepseek.com.evil.com` | 拦 | endpoint 1 条 |
| 前缀伪装 `evilapi.deepseek.com` | 拦 | endpoint 1 条 |
| 通配 `*.deepseek.com` | 命中裸域与子域，不吃伪装域 | endpoint 4 条 |
| 没权限的域名点保存 | 不写 storage + 报错点名域名 + 列出允许名单 | options 4 条 |
| 没权限的域名点「测试连接」 | 不发请求，同一道校验 | options 2 条 |
| 空 Key 点「测试连接」 | 先提示填 Key，不发请求 | options 2 条 |

配置：`http://localhost/*` 与 `http://127.0.0.1/*` 已在 manifest 里（本机 Ollama / vLLM），端口不影响判定。

变异测试：把 `src/options.js` 里两道 `if (!allow.ok) return show(originError(allow), true);` 删掉后重跑 `test/options.test.mjs`，6 条变红；恢复后 21 条全绿。

`node test/run-all.mjs` 现在 **269 条断言**（原 171 + endpoint 30 + options 21 + transcript 27 + diag 20），不需要网络、不花钱。
## 八、没配 API Key 也能拿到字幕全文（W2-3）

为什么要有这条：闸门跑完的那一刻，字幕已经在手里了，但以前只有模型返回之后才有「笔记」，所以没填 Key 的用户点「导出」得到的是一份只有标题和 BV 号的空文件——看起来像产品坏了。

现在的行为：点「导出」时如果还没有任何 AI 笔记，导出的是**字幕全文**。

| 检查 | 行为 | 对应断言 |
| --- | --- | --- |
| frontmatter | `notes: transcript-only`、`source`、`subtitle_source`、`verified` 都写上 | transcript 4 条 |
| 逐句 | 每句一行 `- [mm:ss](可点链接) 原句` | transcript 2 条 |
| 时间格式 | 61.4 秒 → `01:01`；3725 秒 → `62:05`（分钟不封顶，不写成 `01:02:05`） | transcript 2 条 |
| 多 P | 写 `page: 2/5` 与 `part`，标题带「（P2/5 · 下半场）」 | transcript 2 条 |
| 句内换行 | 压成一行，避免 Markdown 列表断成半句 | transcript 1 条 |
| 画面字幕来源 | 额外写 `subtitle_note: 画面字幕识别，可能有错字` | transcript 2 条 |
| 空字幕 | 不崩，正文写清「可能未登录 / 作者没开 AI 字幕 / 接口没返回」 | transcript 2 条 |
| 缺参数 | `sentences` 为 null 不抛异常；没有跳转函数时退化成 `#t=5` | transcript 2 条 |

状态条文案也改了：队列因为 `no-key` 停下时，不再说「模型调用失败」，而是「还没填 API Key：现在点「导出」能拿到字幕全文（N 句，带时间戳）；想变成带引文的结论就点「设置」填一个」。

真浏览器验证（2026-11-14，预览页 + 假数据）：起 `node test/preview-server.mjs 8799`，在浏览器里打开 `/video/BV1TESTPREVIEW`（假 chrome API + 60 句假字幕），把 `window.__bnState.notes` 清空后点面板上的「导出」——浏览器真的下载了 `光合作用 · 假数据预览.md`：6,671 字节 / 77 行 / 60 条 `- [mm:ss](链接) 原句` / frontmatter 里 `notes: transcript-only`。这证明「没有 AI 笔记 → 导出字幕全文」的分支在真实 DOM 里确实被走到。
仍未验证：真扩展环境（真 chrome API、真 B站 页面）里同一次点击——预览页的假 chrome 与真扩展不同，这一步要真机。
## 九、出错时的一键诊断（W2-4）

为什么要有：陌生人报「字幕拿不到」时，来回问「哪个视频 / 什么判定 / 什么端点」要花三四轮，很多人问一轮就走了。所以状态条不是绿色（warn 或 bad）时，面板会多出一个「复制诊断」，点一下拿到：

| 内容 | 例子 | 为什么需要 |
| --- | --- | --- |
| 版本 | `bili-notes 0.7.3` | 老版本的问题可能已经修了 |
| 页面 | `https://www.bilibili.com/video/BV1xx411c7mD?p=2（P2/5）` | 复现必须有 BV 号；推广参数（`spm_id_from`、`vd_source`）会被去掉 |
| 字幕判定 | `stable · 4 次取样一致 · ai-zh · 412 句` | 区分「拿不到」和「拿到了但不对」 |
| 端点 | `api.deepseek.com · 模型 deepseek-chat · Key 已填` | 只写域名与「填没填」，**不写 Key 内容** |
| 本机 OCR | `可用` / `不可用（轻量包或缺文件）` | 轻量包没有 OCR 是设计如此，不是 bug |
| 状态 | `bad · 没有字幕` | 状态条原话 + detail |

断言（`test/diag.test.mjs`，20 条）：推广参数被去掉；`P2/5` 只在多 P 时出现；没填 Key 写「Key 未填」；`ocr` 缺字段就不写这一行；标题/详情里的换行压平；超长标题截 160、详情截 200；坏 URL 原样保留不抛；空对象与 `undefined` 不崩；**输出里绝不出现 `sk-` 或 `apiKey` 字段**。

变异测试：把 `clean()` 里的空白压缩去掉 → 换行那条变红；恢复后 20 条全绿。

切到 `warn` 也显示按钮：用户报得最多的「字幕只有一部分 / 单次取样」都是 warn，只在 bad 时给按钮会漏掉一半报告。

真浏览器验证（2026-11-14，预览页 + 假数据）：把 `navigator.clipboard` 置空模拟「没有剪贴板权限」→ 调用面板按钮的处理函数 → 走 `execCommand('copy')` 兜底并返回成功（状态条回到绿色、按钮收起），复制到的文字是：

```
bili-notes ? · 2026-11-14T12:15:07.806Z
页面: http://127.0.0.1:8799/video/BV1TESTPREVIEW
标题: 光合作用 · 假数据预览
字幕: stable · ai-zh · 60 句
状态: bad
```

版本号显示 `?` 是因为预览页的假 chrome 没有 `getManifest`；「端点 / 模型 / Key」那两行由 background 的 `diag` 消息提供，预览页没有这个假接口，所以只由单测覆盖。
## 十、还没验证的（别当成全跑通了）

- 除 DeepSeek 之外厂商（OpenAI / 通义 / 智谱 / Moonshot）的真实调用、限流、超长视频下的成本。
- 画面字幕在「手写板书 / 极长单句 / 字幕贴画面中部」的视频上；
- 画面字幕的错字率没有量化过（只有耶鲁公开课一条人工看过）。
- 投票防不住「某次接口连着 3 次返回同一份错文件」（原理上防不住，目前没样本）。
- 抽样转写音频和字幕比文字（ASR 校验）没做。
